# Полное математическое описание DST-алгоритма системы JAcademicSupport

> **Версия документа:** август 2026  
> **Реализация:** Spring Boot (Java), PostgreSQL  
> **Ключевые файлы:** `DstCombinationService.java`, `DstLevel0/1/2Service.java`, `DstQueryService.java`, `AbstractBpaSourceProvider.java`, `VacBpaSourceProvider.java`, `ExpBpaSourceProvider.java`, `FcBpaSourceProvider.java`, `VacancyClusterScoreService.java`, `ProfessionClusterService.java`

---

## 1. Введение

Система использует теорию Демпстера–Шафера (DST, Dempster–Shafer Theory) — математическую модель рассуждений в условиях неопределённости. В отличие от классической теории вероятностей, DST позволяет явно выражать **неопределённость** (незнание): масса может быть назначена не только отдельным гипотезам, но и их объединениям.

**Цель алгоритма** — определить, насколько текущая рабочая программа дисциплины (РПД) учебного плана соответствует рыночному спросу на ИТ-компетенции, и сформировать управленческие рекомендации для методистов.

**Принцип работы**: Три независимых источника (вакансии, эксперты, форсайт) поставляют свидетельства о важности технологии. Каждое свидетельство преобразуется в распределение масс BPA = {m(T), m(U), m(F)}, затем источники объединяются правилом Демпстера или Ягера. Итоговая пигнистическая вероятность BetP(T) сравнивается с долей охвата в РПД s_c, и разность Δ = BetP(T) − s_c формирует рекомендацию.

## 3. Архитектурный обзор: четырёхуровневая иерархия

Алгоритм организован в четыре вложенных уровня анализа:

```
┌──────────────────────────────────────────────────────────┐
│ УРОВЕНЬ 0 — Профессия → Домены (DstLevel0Service)         │
│ Q0: Достаточно ли каждый домен покрыт в РПД?             │
│ Вход: вакансии/эксперты/форсайт по профессии и домену    │
│ Выход: BetP(домен), Δ = BetP(T) − s_c(домен)             │
└──────────────────────────┬───────────────────────────────┘
                           ↓ для каждого домена
┌──────────────────────────┴───────────────────────────────┐
│ УРОВЕНЬ 1 — Домен → Технологические семейства             │
│            (DstLevel1Service)                             │
│ Q1: Правильный ли баланс семейств в РПД для этого домена? │
│ Выход: BetP(семейство), Δ = BetP(T) − s_c(семейство)     │
└──────────────────────────┬───────────────────────────────┘
                           ↓ для каждого семейства
┌──────────────────────────┴───────────────────────────────┐
│ УРОВЕНЬ 2 — Семейство → Навыки стека (DstLevel2Service)   │
│ Q2: Какие конкретные навыки включить/убрать из РПД?      │
│ Выход: BetP(навык), Δ, рекомендация                      │
└──────────────────────────┬───────────────────────────────┘
                           ↓ для навыков с версиями
┌──────────────────────────┴───────────────────────────────┐
│ УРОВЕНЬ 3 — Навык → Версии                                │
│ Q3: Актуальна ли версия, преподаваемая в РПД?            │
│ Выход: version_currency, version_gap                     │
└──────────────────────────────────────────────────────────┘
```

## 4. Входные данные как множества

### 4.1. Базовые множества данных

```
𝒫 = {P₁, P₂, …, P_k}        — множество профессий в учебном плане
𝒟 = {D₁, D₂, …}              — множество доменов (BACKEND, DEVOPS, …)
ℱ = {F₁, F₂, …}              — множество технологических семейств
𝒰 = {U₁, U₂, …}              — множество канонических навыков (skill_canonical)

𝒱 = {v₁, v₂, …, v_m}         — множество вакансий на рынке
ℰ = {e₁, e₂, …, e_l}         — множество экспертных оценок
𝒞 = {c₁, c₂, …, c_q}         — множество форсайт-прогнозов
```

### 4.2. Учебный план

Учебный план задаётся кортежем:

**𝒦 = ⟨id, 𝒫_w, 𝒬⟩**

где:

**𝒫_w = { (Pᵢ, pw_i) | Pᵢ ∈ 𝒫, ∑ᵢ pw_i = 1 }** — множество профессий с нормированными весами,

**𝒬 = { (qⱼ, hⱼ, Covⱼ) }** — множество дисциплин учебного плана,

**Covⱼ ⊂ 𝒬_cov** — покрытие дисциплины qⱼ по навыкам/семействам/доменам; каждая запись имеет вид: **(u? | f? | d?, часы)**, где u — канонический навык, f — технологическое семейство, d — домен.

**Где:**
- Pᵢ — код профессии i
- pw_i — нормированный вес профессии i (доля в учебном плане)
- qⱼ — j-я дисциплина
- hⱼ — объём дисциплины qⱼ в академических часах
- Covⱼ — множество записей покрытия дисциплины qⱼ

### 4.3. Вакансия-кластер: предвычисленные оценки

Перед запуском DST-алгоритма выполняется предварительный пайплайн, заполняющий три таблицы:
- `profession_cluster` — вес профессия × кластер
- `vacancy_cluster_score` — оценка вакансия × кластер
- `vacancy_domain` — основной домен каждой вакансии

## 5. Предварительный пайплайн

### 5.1. Вес профессия–кластер (ProfessionClusterService)

Для каждой пары (профессия P, кластер C) вычисляется вес:

$$
ω(P, C) = \frac{|\{v \in \mathcal{V}_P : \mathcal{S}(v) \cap C \neq \emptyset\}|}{|\mathcal{V}_P|}
$$

> ω(P, C) = |{ v ∈ 𝒱_P : 𝒮(v) ∩ C ≠ ∅ }| / |𝒱_P|

**Где:**
- ω(P, C) — вес профессии P для кластера C
- 𝒱_P = { v ∈ 𝒱 : d(v) соответствует профессии P } — вакансии профессии P
- 𝒮(v) — множество канонических навыков вакансии v
- 𝒮(v) ∩ C ≠ ∅ — среди навыков вакансии v найдётся хотя бы один из кластера C
- |𝒱_P| — общее число вакансий профессии P

**Смысл**: доля вакансий профессии P, в которых упоминается хотя бы один навык кластера C.

### 5.2. Оценка вакансия–кластер (VacancyClusterScoreService)

Для каждой пары (вакансия v, кластер C) вычисляется взвешенная оценка на основе расположения навыков в тексте вакансии и зависимостей:

**Шаг 1. Веса расположения навыка в тексте:**

| Поле вакансии | Вес w_loc |
|---------------|-----------|
| Заголовок (title) | 1.0 |
| Список навыков (skills list) | 0.8 |
| Описание (description) | 0.5 |
| Через зависимость (implied) | w_dep ∈ [0.30, 1.0] |

**Шаг 2. Накопление сырого score для пары (v, C):**

> s_raw(v, C) = ∑_{s ∈ 𝒮_C} μ(s, v) · w_loc(s, v)

**Где:**
- s_raw(v, C) — сырой score вакансии v по кластеру C
- 𝒮_C — множество канонических навыков кластера C
- μ(s, v) — максимальный вес расположения навыка s в вакансии v среди всех мест его упоминания
- w_loc(s, v) — вес расположения навыка s в конкретном поле вакансии v (см. таблицу выше)

Если u ∈ 𝒮(v) и существует дуга (u, s) в графе зависимостей 𝒢, где s ∈ C:

> s_raw(v, s) += min(δ(u, s) · ρ_dep,  1.0)

**Где:**
- u — навык, явно упоминаемый в вакансии v; s — навык кластера C, зависящий от u
- δ(u, s) — вес дуги зависимости (u, s) в графе 𝒢
- ρ_dep — мультипликатор implied-веса

**Шаг 3. Нормировка по максимальному score:**

> s̃(v, C) = s_raw(v, C) / max_{C' ∈ 𝒞_all} s_raw(v, C')

**Где:**
- s̃(v, C) — нормированный score вакансии v по кластеру C ∈ [0, 1]
- 𝒞_all — множество всех кластеров
- max_{C' ∈ 𝒞_all} s_raw(v, C') — максимальный сырой score по всем кластерам для данной вакансии v

Нормировка выполняется per-вакансия, так что лучший кластер получает s̃ = 1.0.

**Хранение:** Результат записывается в `vacancy_cluster_score(vacancy_id, cluster_id, score)`.

## 6. Источники доказательств (Evidence Sources)

Алгоритм использует три источника свидетельств. Для каждого уровня (L0/L1/L2) источники возвращают пару `(relevantCount, averageScore)` с разными фильтрами выборки.

### 6.1. VAC — Вакансии (Vacancy Market)

**Параметры источника:**

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| λ_vac (L1/L2) | 15.0 | 15 вакансий → κ ≈ 0.63; стандартный объём рынка ИТ |
| λ_vac_domain (L0) | 2.0 | Доменный уровень: 2 «домен-вакансии» → κ ≈ 0.63 |
| w_vac | 0.80 | Реальные данные, но есть дубли и сезонность |

**Способ вычисления n (relevantCount), N (totalCount) и σ (averageScore) по уровням:**

*Уровень 0 (домен D, профессия P):*

> N = |𝒱_P|
>
> n(D, P) = |{ v ∈ 𝒱_P : d(v) = D }|
>
> σ = 1.0  (частота как мера важности; отдельный score не используется)
>
> λ = λ_vac_domain = 2.0

*Уровень 1 (семейство F, домен D, профессия P):*

> N = |𝒱_{P,D}|
>
> n(F, D, P) = |{ v ∈ 𝒱_{P,D} : 𝒮(v) ∩ 𝒮_F ≠ ∅ }|
>
> σ = 1.0
>
> λ = λ_vac = 15.0

*Уровень 2 (навык U, семейство F, домен D, профессия P):*

> N = |𝒱_{P,D}|
>
> n(U, P) = |{ v ∈ 𝒱_{P,D} : U ∈ 𝒮(v) }|
>
> σ = 1.0
>
> λ = λ_vac = 15.0

**Где:**
- 𝒱_P — вакансии профессии P
- 𝒱_{P,D} = { v ∈ 𝒱_P : d(v) = D } — вакансии профессии P в домене D
- d(v) — домен вакансии v
- 𝒮(v) — множество канонических навыков вакансии v
- 𝒮_F — множество канонических навыков семейства F
- f(s) = F — навык s принадлежит семейству F (используется при формировании 𝒮_F)

### 6.2. EXP — Экспертные оценки (Expert Opinions)

**Параметры источника:**

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| λ_exp (L1/L2) | 5.0 | 5 экспертов → κ ≈ 0.63; типичная экспертная группа |
| λ_exp_domain (L0) | 1.0 | Меньше экспертов на домен, порог понижен |
| w_exp | 0.90 | Профессиональные взвешенные оценки, минимальный шум |

**Способ вычисления:**

*Уровень 0 (домен D, профессия P):*

> N = 12  (TOTAL_EXPERTS — фиксированная константа)
>
> n(D, P) = |{ e ∈ ℰ_{P,D} : ρ(e) > 0 }|
>
> σ(D, P) = (1 / |ℰ_{P,D}|) · ∑_{e ∈ ℰ_{P,D}} ρ(e) / ρ_max  ∈ [0, 1]
>
> λ = λ_exp_domain = 1.0

*Уровень 1 (семейство F, домен D, профессия P):*

> N = 12  (TOTAL_EXPERTS)
>
> n(F, D, P) = |ℰ_{P,F}|
>
> σ(F, D, P) = (1 / |ℰ_{P,F}|) · ∑_{e ∈ ℰ_{P,F}} ρ(e) / ρ_max
>
> λ = λ_exp = 5.0

*Уровень 2 (навык U, профессия P):*

> N = 12  (TOTAL_EXPERTS)
>
> n(U, P) = |ℰ_{P,U}|
>
> σ(U, P) = (1 / |ℰ_{P,U}|) · ∑_{e ∈ ℰ_{P,U}} ρ(e) / ρ_max
>
> λ = λ_exp = 5.0

**Где:**
- ℰ — множество экспертных оценок
- ℰ_{P,D} = { e ∈ ℰ : профессия P, домен D } — оценки по домену D и профессии P
- ℰ_{P,F} = { e ∈ ℰ : профессия P, семейство F } — оценки по семейству F и профессии P
- ℰ_{P,U} = { e ∈ ℰ : профессия P, навык U } — оценки по навыку U и профессии P
- ρ(e) — числовая оценка эксперта e
- ρ_max — максимальное значение шкалы оценивания

### 6.3. FC — Форсайт (Foresight)

**Параметры источника:**

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| λ_fc (L1/L2) | 2.0 | 2 прогноза → κ ≈ 0.63; прогнозов в БД мало |
| λ_fc_domain (L0) | 0.5 | Ещё меньше прогнозов на домен |
| w_fc | 0.60 | Прогнозы часто ошибаются, рынок ИТ меняется быстро |

**Способ вычисления:**

> N = 4  (TOTAL_SOURCES — число форсайт-источников, фиксированная константа)
>
> n(X, P) = |{ c ∈ 𝒞_{X,P} : γ(c) > 0 }|
>
> σ(X, P) = (1 / |𝒞_{X,P}|) · ∑_{c ∈ 𝒞_{X,P}} π(c)
>
> λ = λ_fc (L1/L2) или λ_fc_domain (L0) — в зависимости от уровня

**Где:**
- 𝒞 — множество форсайт-прогнозов
- 𝒞_{X,P} — прогнозы по объекту X (навык U, домен D или семейство F) и профессии P
- γ(c) — прогнозируемый прирост спроса по прогнозу c
- π(c) — коэффициент уверенности прогноза c ∈ [0, 1]

---

## 7. Шаг 1: Вычисление κ — коэффициент уверенности по объёму данных

### 7.1. Формула (текущая реализация: экспоненциальное насыщение)

Реализовано в `DstQueryService.computeBpa()`:

> **κ = 1 − exp(−λ · n / N)**

**Где:**
- κ ∈ [0, 1] — коэффициент уверенности источника
- n — число релевантных записей источника (relevantCount)
- N — общий объём источника (totalCount)
- λ — константа сглаживания («полудоверие»), индивидуальная для каждого источника и уровня
- exp(·) — функция натуральной экспоненты

**Свойства формулы:**
- При `n = 0`: κ = 0 (нет данных → нет уверенности)
- При `n/N → 1`: κ → 1 − e^(−λ) (максимальная уверенность ограничена)
- При `n/N = 1/λ`: κ = 1 − e^(−1) ≈ 0.632 («полудоверие»)
- Монотонно возрастает с ростом `n`

**Выбор экспоненциального закона:** По сравнению с линейной функцией, экспоненциальное насыщение отражает убывающую отдачу от новых данных — каждая дополнительная вакансия при большом `n` добавляет меньше уверенности, чем при малом `n`.

### 7.2. Разные λ по уровням

| Источник | Уровень | λ | Значение «полудоверия» |
|----------|---------|---|------------------------|
| VAC | L1, L2 (семейство/навык) | 15.0 | При 15 вакансиях из N κ ≈ 0.63 |
| VAC | L0 (домен) | 2.0 | При 2 из N κ ≈ 0.63 |
| EXP | L1, L2 | 5.0 | При 5 из 12 экспертов κ ≈ 0.63 |
| EXP | L0 | 1.0 | При 1 из 12 экспертов κ ≈ 0.63 |
| FC | L1, L2 | 2.0 | При 2 из 4 форсайтов κ ≈ 0.63 |
| FC | L0 | 0.5 | При 0.5 из 4 форсайтов κ ≈ 0.63 |

**Обоснование разных λ:** На доменном уровне (L0) данные более агрегированы — одна «вакансия в домене» уже несёт более весомую информацию, поэтому λ_domain < λ_local.

## 8. Шаг 2: Базовое распределение масс (BPA)

### 8.1. Формула вычисления BPA из сырых данных

Выполняется в `DstQueryService.computeBpa()` и `AbstractBpaSourceProvider.buildResult()`:

**Этап A: computeBpa() — из БД в сырой BpaResult:**

> κ = 1 − exp(−λ · n / N)
>
> m(T) = κ · σ
>
> m(Θ) = 1 − m(T)

**Где:**
- κ — коэффициент уверенности (вычислен по формуле раздела 7)
- σ — средняя оценка важности технологии по данному источнику (averageScore)
- m(T) — масса гипотезы «технология важна»
- m(Θ) — масса полной неопределённости (обозначается mTheta в коде)

Промежуточный результат: *(n, N, λ, σ, m(T), m(Θ))*

**Этап B: buildResult() — обогащение в AbstractBpaSourceProvider:**

> m(T) = m(T)  (из этапа A, без изменений)
>
> m(F) = 0.0   (источники VAC/EXP/FC не заявляют «технология не важна»)
>
> m(U) = 1 − m(T)  (вся остаточная масса — неопределённость)

**Где:**
- m(F) = 0, потому что вакансии, эксперты и форсайт сообщают о наличии спроса, но не о его отсутствии — явный сигнал «технология не нужна» в данных не кодируется

> **Почему m(F) = 0?** Вакансии, эксперты и форсайт сообщают о наличии спроса, но не о его отсутствии. Явный сигнал «технология не нужна» в данных не кодируется, поэтому масса на F не назначается.

### 8.2. Тройки BPA для каждого источника

После Шага 2 каждый источник s порождает тройку:

> BPA_s = { m_s(T),  m_s(U),  m_s(F) },    m_s(T) + m_s(U) + m_s(F) = 1

| Источник | m(T) | m(U) = 1 − m(T) | m(F) |
|----------|------|-----------------|------|
| VAC | κ_vac · σ_vac | 1 − m_vac(T) | 0.0 |
| EXP | κ_exp · σ_exp | 1 − m_exp(T) | 0.0 |
| FC  | κ_fc · σ_fc   | 1 − m_fc(T)  | 0.0 |

## 9. Шаг 3: Дисконтирование по надёжности источника

### 9.1. Формулы

Выполняется в `AbstractBpaSourceProvider.buildResult()`:

> m′(T) = w · m(T)
>
> m′(F) = w · m(F)   (= 0.0 для VAC/EXP/FC)
>
> m′(U) = w · m(U) + (1 − w)   = 1 − m′(T) − m′(F)

Нормировка (защита от численных ошибок):

> m′(X) := m′(X) / ( m′(T) + m′(U) + m′(F) )   для X ∈ {T, U, F}

**Где:**
- w — вес надёжности источника ∈ (0, 1]
- m(T), m(U), m(F) — массы до дисконтирования (из Шага 2)
- m′(T), m′(U), m′(F) — дисконтированные массы
- (1 − w) — доля уверенности, переносимая в неопределённость m′(U)

**Смысл операции:** Часть уверенности (1 − w) «перекладывается» из m(T)/m(F) в m(U). Ненадёжный источник получает меньший вклад при комбинировании — не потому что он «не прав», а потому что мы в него меньше верим.

**Эквивалентная форма для m′(U):**

> m′(U) = (1 − w) · 1 + w · m(U)

### 9.2. Зафиксированные веса надёжности

| Источник | w | Обоснование |
|----------|---|-------------|
| EXP | 0.90 | Профессиональные эксперты, согласованные оценки |
| VAC | 0.80 | Фактические данные рынка, но дубли и сезонность |
| FC | 0.60 | Форсайт-прогнозы системно ошибаются в быстрой отрасли |

### 9.3. Пример влияния дисконтирования

Пусть m(T) = 0.70 для VAC (w = 0.80):

> m′(T) = 0.80 · 0.70 = 0.560   (−14.1% от исходного)
>
> m′(U) = 0.80 · 0.30 + 0.20 = 0.440
>
> m′(F) = 0.0

После дисконтирования EXP с тем же m(T) = 0.70 (w = 0.90):

> m′(T) = 0.90 · 0.70 = 0.630   (−5.7% от исходного)
>
> m′(U) = 0.90 · 0.30 + 0.10 = 0.370

EXP сохраняет большую часть уверенности, чем VAC — именно за счёт более высокого w.

## 10. Шаг 4: Адаптивное комбинирование источников

### 10.1. Коэффициент конфликта K

> **K = m₁(T) · m₂(F) + m₁(F) · m₂(T)**

**Где:**
- m₁(T), m₁(F) — дисконтированные массы первого источника (гипотезы «важно» и «не важно»)
- m₂(T), m₂(F) — дисконтированные массы второго источника
- K ∈ [0, 1] — коэффициент конфликта

K измеряет суммарную «конфликтную массу» — ситуации, когда один источник говорит «важно» (T), а другой — «не важно» (F).

- K = 0: источники полностью согласованы
- K ∈ (0, 0.4): незначительный/умеренный конфликт
- K ≥ 0.4: высокий конфликт → применяется правило Ягера

> **В текущих данных VAC/EXP/FC:** так как `m(F) = 0` у всех трёх источников до комбинирования, K между ними всегда равно 0. Конфликт возникает только если в будущем добавить источник с явным сигналом F (например, форсайт на спад технологии).

### 10.2. Правило Демпстера (K < τ_K = 0.40)

Реализовано в `DstCombinationService.combineDST()`.

Числители (до нормировки):

> num(T) = m₁(T)·m₂(T) + m₁(T)·m₂(U) + m₁(U)·m₂(T)
>
> num(U) = m₁(U)·m₂(U)
>
> num(F) = m₁(F)·m₂(F) + m₁(F)·m₂(U) + m₁(U)·m₂(F)

Нормировочный делитель (защита от деления на 0):

> norm = max(1 − K,  0.0001)

Объединённые массы:

> m_out(T) = num(T) / norm
>
> m_out(U) = num(U) / norm
>
> m_out(F) = num(F) / norm

Повторная нормировка (численная защита):

> m_out(X) := m_out(X) / ( m_out(T) + m_out(U) + m_out(F) )   для X ∈ {T, U, F}

**Где:**
- m₁(·), m₂(·) — дисконтированные массы двух объединяемых источников
- norm = 1 − K — перенормировочный делитель, устраняющий конфликтную массу
- m_out(·) — результирующее распределение масс после комбинирования

**Смысл слагаемых в num(T):**

| Слагаемое | Ситуация |
|-----------|----------|
| m₁(T)×m₂(T) | Оба уверены «важно» → масса T усиливается |
| m₁(T)×m₂(U) | Первый уверен T, второй не знает → T сохраняется |
| m₁(U)×m₂(T) | Первый не знает, второй уверен T → T сохраняется |

**Смысл нормировки `1/(1−K)`:** Правило Демпстера «перераспределяет» конфликтную массу пропорционально между T, U, F. При K = 0.3 делитель = 0.7, и все массы вырастают в ×1.43.

### 10.3. Правило Ягера (K ≥ τ_K = 0.40)

Реализовано в `DstCombinationService.combineYager()`.

> m_out(T) = m₁(T)·m₂(T) + m₁(T)·m₂(U) + m₁(U)·m₂(T)
>
> m_out(U) = m₁(U)·m₂(U) + K     ← конфликтная масса K переносится в неопределённость
>
> m_out(F) = m₁(F)·m₂(F) + m₁(F)·m₂(U) + m₁(U)·m₂(F)

Нормировка:

> m_out(X) := m_out(X) / ( m_out(T) + m_out(U) + m_out(F) )   для X ∈ {T, U, F}

**Где:**
- K — коэффициент конфликта (см. раздел 10.1)
- Ключевое отличие от правила Демпстера: конфликтная масса K прибавляется к m_out(U), а не устраняется через нормировку

**Ключевое отличие от Демпстера:** конфликтная масса K не перераспределяется между T и F, а добавляется в U — это «честное признание неопределённости». Ягер консервативнее: при высоком конфликте он увеличивает неопределённость вместо усиления доминирующего мнения.

### 10.4. Адаптивный выбор правила

Реализовано в `DstCombinationService.combineAdaptive()`:

> Если K ≥ τ_K  →  применить правило Ягера
>
> Если K < τ_K  →  применить правило Демпстера

**Где:** τ_K = 0.40 — порог конфликта

### 10.5. Последовательное комбинирование нескольких источников

При наличии N_enabled активных источников комбинирование выполняется **последовательно**:

> m⁽¹⁾ = BPA(источник₁)
>
> m⁽ⁱ⁾ = combineAdaptive( m⁽ⁱ⁻¹⁾, BPA(источникᵢ) )   для i = 2, …, N_enabled
>
> K_итоговый = max( K₁, K₂, …, K_{N_enabled − 1} )

**Где:**
- m⁽ⁱ⁾ — распределение масс после i-го шага комбинирования
- Kᵢ — коэффициент конфликта на i-м шаге
- Правило Демпстера коммутативно и ассоциативно, поэтому порядок источников не влияет на результат

Правило Демпстера **коммутативно и ассоциативно**, поэтому порядок не влияет на результат.

## 11. Шаг 5: Взвешенное агрегирование по нескольким профессиям

Учебный план может охватывать несколько профессий с разными весами `{(P_i, pw_i)}`. В этом случае BPA каждого источника вычисляется отдельно для каждой профессии, а затем взвешенно усредняется.

### 11.1. Нормировка весов профессий

Дано: 𝒫_w = { (Pᵢ, raw_wᵢ) }

> pw_i = raw_wᵢ / ∑ⱼ raw_wⱼ,   ∑ᵢ pw_i = 1

Если ∑ raw_wᵢ = 0: pw_i = 1 / |𝒫|  (равные веса)

**Где:**
- raw_wᵢ — исходный вес профессии Pᵢ в учебном плане (до нормировки)
- pw_i — нормированный вес профессии Pᵢ

### 11.2. Взвешенное усреднение BPA результатов

Реализовано в `DstQueryService.weightedAverage()`.

Для каждой профессии Pᵢ ∈ 𝒫 вычислить BPA_i = source.compute(Pᵢ, context), затем:

> m_avg(T) = ( ∑ᵢ pw_i · m_i(T) ) / ( ∑_{i : m_i(T) > 0} pw_i )

Аналогично усредняются: n (relevantCount), N (totalCount), σ (averageScore), λ.

**Где:**
- m_i(T) — масса гипотезы T для профессии Pᵢ
- сумма в знаменателе берётся только по профессиям с ненулевыми данными

### 11.3. Применение в DstCombinationService

Метод `computeWeighted(ctx, profs, supply, queryService)` выполняет следующую последовательность:

```
1. Для каждого источника (VAC, EXP, FC):
   a. Получить weightedAverage BPA по всем профессиям
   b. Применить buildResult() → получить m′(T), m′(U), m′(F)

2. Собрать список enabled источников

3. Если enabled.size() == 0:
   → BetP = supply, Δ = 0, recommendation = "preserve"

4. Если enabled.size() == 1:
   → использовать единственный источник без комбинирования

5. Иначе: последовательное combineAdaptive()

6. Вычислить BetP, Δ, recommendation
```

## 12. Шаг 6: Пигнистическая вероятность BetP и показатель дефицита Δ

### 12.1. Пигнистическая вероятность (Pignistic Probability)

После комбинирования получены итоговые `m*(T)`, `m*(U)`, `m*(F)`. Для принятия решения нужна одна скалярная мера. Используется преобразование BetP, основанное на **принципе недостаточного основания**: неопределённость `m*(U)` равномерно распределяется между всеми N_CL гипотезами (кластерами/семействами/навыками).

Реализовано в `DstCombinationService.finishCombination()`:

> **BetP(T) = m*(T) + m*(U) / N_CL**

**Где:**
- m*(T) — итоговая масса гипотезы «технология важна» после всех шагов комбинирования
- m*(U) — итоговая масса неопределённости
- N_CL = 25 — оценочное число конкурирующих кластеров/семейств/навыков в программе ИТ (константа)

**Диапазон BetP:** BetP ∈ (0, 1)

**Почему не просто m*(T)?** `m*(U)` — нераспределённая масса. Если из N_CL кластеров/семейств нет дополнительных данных об их приоритете, равномерное распределение неопределённости является наиболее «честной» оценкой. Добавка `m*(U)/N_CL` тем меньше, чем больше кластеров конкурируют за ресурсы.

**Влияние N_CL = 25:** При высокой неопределённости m*(U) = 0.6:
- N_CL = 25 → BetP_добавка = 0.6 / 25 = 0.024
- N_CL = 5  → BetP_добавка = 0.6 / 5  = 0.120

Таким образом, малое N_CL усиливает «оптимистичность» оценки.

### 12.2. Показатель дефицита Δ

> **Δ = BetP(T) − s_c**

**Где:**
- BetP(T) — пигнистическая вероятность гипотезы «технология важна» (см. раздел 12.1)
- s_c ∈ [0, 1] — доля охвата технологии/домена/семейства в РПД учебного плана (см. раздел 14)
- Δ ∈ [−1, 1] — показатель дефицита: положительный означает недостаточное покрытие в РПД, отрицательный — избыточное

**Интерпретация:**

| Значение Δ | Интерпретация |
|-----------|---------------|
| Δ > +0.15 | **Дефицит**: рынок требует больше, чем отведено в РПД |
| −0.15 ≤ Δ ≤ +0.15 | **Баланс**: программа соответствует рыночным требованиям |
| Δ < −0.15 | **Избыток**: в РПД больше ресурсов, чем требует рынок |

## 13. Шаг 7: Принятие решения

### 13.1. Алгоритм (DstCombinationService.decide())

Правила применяются последовательно; первое выполнившееся условие задаёт результат:

**Шаг A — устаревание:**

> Если m*(F) > 0.8  ∧  m*(T) < 0.1  →  **"obsolete"**

**Шаг B — дефицит при надёжных данных:**

> Если Δ > τ_Δ  ∧  K ≤ τ_K:
>
> &nbsp;&nbsp;&nbsp;&nbsp;clearSignal = ( m*(U) ≤ τ_Θ ) ∨ ( Δ > 0.35 )
>
> &nbsp;&nbsp;&nbsp;&nbsp;Если clearSignal:
>
> &nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;Если Δ > 0.5  →  **"strong"**
>
> &nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;Иначе  →  **"moderate"**

**Шаг C — избыток в РПД:**

> Если Δ < −τ_Δ  →  **"reduce"**

**Шаг D — неопределённость или конфликт:**

> Если K > τ_K  ∨  m*(U) > τ_Θ  →  **"expertise"**

**Шаг E — баланс (по умолчанию):**

> →  **"preserve"**

**Где:**
- m*(T), m*(U), m*(F) — итоговые массы после комбинирования всех источников
- Δ = BetP(T) − s_c — показатель дефицита (раздел 12.2)
- K — итоговый коэффициент конфликта
- τ_Δ = 0.15, τ_K = 0.40, τ_Θ = 0.15 — пороговые значения

### 13.2. Пороговые значения

| Параметр | Значение | Смысл |
|----------|----------|-------|
| τ_Δ | 0.15 | Минимальный дефицит для рекомендации «усилить» или «сократить» |
| τ_K | 0.40 | Порог конфликта: выше → Ягер + рекомендация «экспертиза» |
| τ_Θ | 0.15 | Порог неопределённости: выше → рекомендация «экспертиза» |

### 13.3. Таблица решений

| m*(F) > 0.8? | Δ > τ_Δ? | K ≤ τ_K? | m*(U) ≤ τ_Θ или Δ > 0.35? | Δ > 0.5? | Δ < −τ_Δ? | Результат |
|---|---|---|---|---|---|---|
| ✅ (и m*(T) < 0.1) | — | — | — | — | — | **obsolete** |
| ❌ | ✅ | ✅ | ✅ | ✅ | — | **strong** |
| ❌ | ✅ | ✅ | ✅ | ❌ | — | **moderate** |
| ❌ | ✅ | ✅ | ❌ | — | — | **expertise** |
| ❌ | ✅ | ❌ | — | — | — | **expertise** |
| ❌ | ❌ | — | — | — | ✅ | **reduce** |
| ❌ | ❌ | ❌/✅ | — | — | ❌ | **expertise** / **preserve** |
| ❌ | ❌ | ✅ | ✅ | — | ❌ | **preserve** |

### 13.4. Смысловая интерпретация кодов решений

| Код | Рекомендация для методиста |
|-----|---------------------------|
| `strong` | Значительно увеличить долю технологии в РПД (Δ > 0.5) |
| `moderate` | Умеренно увеличить долю (0.15 < Δ ≤ 0.5) |
| `reduce` | Сократить долю в РПД (Δ < −0.15) |
| `expertise` | Требуется дополнительная экспертная оценка (высокий K или m*(U)) |
| `preserve` | Текущее покрытие оптимально — сохранить |
| `obsolete` | Технология устарела: рассмотреть исключение из РПД |

## 14. Вычисление s_c — доля охвата в РПД

s_c — это скалярное число ∈ [0, 1], отражающее долю учебного времени (часов), выделенных на данную технологию/домен/семейство в рамках анализируемого учебного плана или дисциплины.

### 14.1. Уровень 0: s_c по домену D (DstLevel0Service)

Источник данных: записи покрытия дисциплины, каждая имеет вид `(u? | f? | d?, hours)`.

**Алгоритм:**

1. Для каждой дисциплины qⱼ ∈ 𝒬 разрешить домен каждой записи покрытия по приоритету: собственный домен → домен канонического навыка → домен семейства (3-шаговый fallback). Выбрать наиболее детальный уровень (DOMAIN > FAMILY > SKILL):

   > h̃_D(qⱼ, D) = max_level{ hours(D, level) }  — эффективные часы домена D в дисциплине qⱼ

2. Пропорциональные часы домена D в дисциплине qⱼ:

   > φⱼ(D) = h̃_D(qⱼ, D) / ∑_{D'} h̃_D(qⱼ, D')
   >
   > H_prop(D) = ∑ⱼ φⱼ(D) · hⱼ

3. Итоговое значение s_c для домена D:

   > s_c(D) = H_prop(D) / H_total

**Где:**
- h̃_D(qⱼ, D) — эффективные часы домена D в дисциплине qⱼ
- φⱼ(D) — доля домена D в часах дисциплины qⱼ
- hⱼ — полный объём дисциплины qⱼ в академических часах
- H_total = ∑ⱼ hⱼ — суммарный объём учебного плана

### 14.2. Уровень 1: s_c по технологическому семейству F (DstLevel1Service)

1. Для каждой дисциплины qⱼ и целевого домена D разрешить часы по семейству F (приоритет: собственное семейство → семейство канонического навыка, fallback «Прочее»):

   > h̃_F(qⱼ, F, D) — эффективные часы семейства F в дисциплине qⱼ в рамках домена D

2. Пропорциональные часы семейства F в домене D:

   > φⱼ(F, D) = h̃_F(qⱼ, F, D) / ∑_{F'} h̃_F(qⱼ, F', D)
   >
   > H_fam(F, D) = ∑ⱼ φⱼ(F, D) · hⱼ

3. Итоговое значение s_c для семейства F:

   > s_c(F, D) = min(1,  H_fam(F, D) / ∑_{F'} H_fam(F', D))

**Где:**
- H_fam(F, D) — суммарные пропорциональные часы семейства F в домене D по всем дисциплинам

### 14.3. Уровень 2: s_c по навыку U (DstLevel2Service)

1. Для каждой дисциплины qⱼ разрешить пропорциональные часы навыка U:

   > fraction(U, qⱼ) = hours(U, qⱼ) / ∑_{U' ∈ F_D} hours(U', qⱼ)
   >
   > H_can(U) = ∑ⱼ fraction(U, qⱼ) · hⱼ

2. Итоговое значение s_c для навыка U:

   > s_c(U) = min(1,  H_can(U) / ∑_{U' ∈ F_D} H_can(U'))

**Где:**
- H_can(U) — суммарные пропорциональные часы канонического навыка U по всем дисциплинам
- F_D — множество навыков семейства F в домене D

## 15. Уровень 0: Полный алгоритм анализа доменов

**Вход:** `curriculumId`  
**Выход:** `DstL0Response` — список доменов с BetP, Δ, recommendation, sources

**Последовательность шагов:**

1. Загрузить 𝒦 → 𝒫_w с весами, 𝒬 (дисциплины)

2. Нормировка весов: pw_i = raw_wᵢ / ∑ⱼ raw_wⱼ

3. Вычислить H_total = ∑ⱼ hⱼ

4. Для каждой дисциплины qⱼ ∈ 𝒬 вычислить эффективные часы доменов:
   > h̃_D(qⱼ, D) — по приоритету DOMAIN > FAMILY > SKILL
   >
   > φⱼ(D) = h̃_D(qⱼ, D) / ∑_{D'} h̃_D(qⱼ, D')
   >
   > H_prop(D) += φⱼ(D) · hⱼ

5. Собрать множество доменов:
   > 𝒟_all = ( ∪ᵢ domains(Pᵢ) ) ∪ 𝒟_rpd

6. Для каждого домена D ∈ 𝒟_all:
   > s_c(D) = H_prop(D) / H_total
   >
   > BetP(T), Δ, recommendation ← computeWeighted( ctx(D), 𝒫_w, s_c(D) )  (шаги κ→BPA→m′→m*→BetP→Δ→решение)

7. Сортировать домены по BetP(T) убыванию → вернуть DstL0Response

**API:** `GET /api/dst/curriculum/{id}/level0`

## 16. Уровень 1: Полный алгоритм анализа технологических семейств

**Вход:** `curriculumId`, `domain`  
**Выход:** `DstL1Response` — список семейств с BetP, Δ, recommendation

**Последовательность шагов:**

1. Загрузить 𝒦 → 𝒫_w, 𝒬

2. Для каждой дисциплины qⱼ ∈ 𝒬 агрегировать эффективные часы семейств в домене D:
   > h̃_F(qⱼ, F, D) — по приоритету FAMILY > SKILL
   >
   > φⱼ(F, D) = h̃_F(qⱼ, F, D) / ∑_{F'} h̃_F(qⱼ, F', D)
   >
   > H_fam(F) += φⱼ(F, D) · hⱼ

3. H_dom = ∑_F H_fam(F)

4. Собрать множество семейств:
   > ℱ_all = ( ∪ᵢ families(Pᵢ, D) ) ∪ ℱ_rpd

5. N_fam = max(1, |∪ᵢ families(Pᵢ, D)|)  — используется в знаменателе BetP(T)

6. Для каждого семейства F ∈ ℱ_all:
   > s_c(F) = min(1,  H_fam(F) / H_dom)
   >
   > BetP(T) = m*(T) + m*(U) / N_fam    ← N_fam вместо N_CL = 25
   >
   > Δ, recommendation ← аналогично L0

7. Сортировать по BetP(T) убыванию → вернуть DstL1Response

> **Ключевое отличие L1:** знаменатель пигнистической вероятности равен N_fam (реальное число семейств в домене), а не константе N_CL = 25. Это повышает точность для доменов с малым числом семейств.

**API:** `GET /api/dst/curriculum/{id}/level1?domain=BACKEND`

## 17. Уровень 2: Полный алгоритм анализа навыков стека

**Вход:** `curriculumId`, `domain`, `techFamily`  
**Выход:** `DstL2Response` — список канонических навыков с BetP, Δ, recommendation

**Последовательность шагов:**

1. Загрузить 𝒦 → 𝒫_w, 𝒬

2. Для каждой дисциплины qⱼ ∈ 𝒬 агрегировать часы по навыкам U в (D, F):
   > fraction(U, qⱼ) = hours(U, qⱼ) / ∑_{U'} hours(U', qⱼ)
   >
   > H_can(U) += fraction(U, qⱼ) · hⱼ

3. H_fam = ∑_{U ∈ F_D} H_can(U)

4. Собрать множество навыков:
   > 𝒰_all = ( ∪ᵢ 𝒮(Pᵢ, D, F) ) ∪ 𝒰_rpd

5. N_sk = max(1, |∪ᵢ 𝒮(Pᵢ, D, F)|)  — используется в знаменателе BetP(T)

6. Для каждого навыка U ∈ 𝒰_all:
   > s_c(U) = min(1,  H_can(U) / H_fam)
   >
   > BetP(T) = m*(T) + m*(U) / N_sk    ← N_sk вместо N_CL = 25
   >
   > Δ, recommendation ← аналогично L0

7. Сортировать по BetP(T) убыванию → вернуть DstL2Response

**API:** `GET /api/dst/curriculum/{id}/level2?domain=BACKEND&techFamily=Java`

## 18. Уровень 3: Актуальность версий (version currency)

### 18.1. Концепция

Навык может быть покрыт в РПД, но в устаревшей версии. Например, учебный план содержит Java 8, тогда как рынок требует Java 17. Уровень 3 вычисляет **коэффициент актуальности версии** vc и корректирует s_c.

### 18.2. Источник данных

- Таблица `skill_version`: `(canonical_id, raw_string, version_min, version_max, is_plus)`
- Таблица `skill_canonical`: `version_group` — группирует версии одного продукта

Версии вакансий берутся через siblings: `skill_canonical WHERE version_group = target.version_group AND id != target.id`.

**API:** `GET /api/dst/skills/{canonicalId}/versions`

### 18.3. Формулы (плановые, из ALGORITHM_IDEAL_V2.md)

**1. Рыночные ориентиры** (из version_group siblings):

> v_med = медиана( { версии по вакансиям, взвешенная по absoluteCount } )
>
> v_max = максимальная версия рынка

**2. Отставание:**

> gap = v_med − v_rpd   (со знаком; целое число для мажорных версий)

**Где:**
- v_rpd — версия навыка U, преподаваемая в РПД
- gap > 0 означает отставание, gap ≤ 0 — актуальность или опережение

**3. Коэффициент актуальности версии:**

| gap | vc(gap) | Интерпретация |
|-----|---------|---------------|
| ≤ 0 | 1.00 | Актуально или опережает рынок |
| 1   | 0.80 | Небольшое отставание |
| 2   | 0.50 | Предупреждение |
| 3   | 0.25 | Значительное отставание |
| ≥ 4 | 0.10 | Критическое устаревание |

**4. Скорректированное покрытие:**

> s_c_eff(U) = s_c(U) · vc(gap)

**Где:**
- vc(gap) — коэффициент актуальности версии
- s_c_eff(U) — эффективная доля охвата навыка U с учётом устаревания версии

> **Статус реализации:** Frontend отображает версии с частотностью по вакансиям. Формула vc и коррекция s_c — запланированы, не внедрены в текущий `DstCombinationService`.

**Режимы Level 1:**
- `По доменам` — показывает домены с частотными bar-чартами; при выборе домена → семейства → навыки
- `По группам` — показывает кластеры `skills_group` с весом `professionWeight`

selectProfession(code)

               → GET /api/dst/.../domain-clusters/{domain}/skills

**Panel «Связанные» (Related):**

При клике на навык открывается правая панель с:
- **Версии:** `GET /api/dst/skills/{id}/versions` → bar-chart версий по частоте в вакансиях
- **Связанные навыки:** `GET /api/dst/skills/{id}/related` → top-50 co-occurrence навыков

## 21. Сквозной пример вычисления

**Контекст:** Учебный план «Бэкенд-разработчик», одна профессия «backend» (pw = 1.0), анализируем домен BACKEND.

**Дано (из БД):**
- Всего вакансий профессии P: N = 1000
- Вакансий с domain = BACKEND: n = 950 → κ_vac = 1 − exp(−2 × 950/1000) = 1 − e^(−1.90) ≈ 0.850
- m_vac(T) = κ_vac × 1.0 = 0.850,  m_vac(U) = 0.150,  m_vac(F) = 0.0
- Дисконтирование w = 0.80: m′_vac(T) = 0.680,  m′_vac(U) = 0.320

- Экспертов по BACKEND: n = 8 из 12 → κ_exp = 1 − exp(−1.0 × 8/12) ≈ 0.487
- avg score экспертов = 0.85 → m_exp(T) = 0.487 × 0.85 = 0.414,  m_exp(U) = 0.586
- Дисконтирование w = 0.90: m′_exp(T) = 0.373,  m′_exp(U) = 0.627

- FC: 1 прогноз из 4 → κ_fc = 1 − exp(−0.5 × 1/4) ≈ 0.118
- avg confidence = 0.70 → m_fc(T) = 0.083,  m_fc(U) = 0.917
- Дисконтирование w = 0.60: m′_fc(T) = 0.050,  m′_fc(U) = 0.950

**Комбинирование VAC ⊕ EXP:**

```
K₁ = m′_vac(T) × m′_exp(F) + m′_vac(F) × m′_exp(T) = 0 + 0 = 0
num(T) = 0.680×0.373 + 0.680×0.627 + 0.320×0.373 = 0.254 + 0.426 + 0.119 = 0.799
num(U) = 0.320 × 0.627 = 0.201
num(F) = 0
norm = 1 − 0 = 1.0
→ m_{1⊕2}(T) = 0.799,  m_{1⊕2}(U) = 0.201
```

**(VAC⊕EXP) ⊕ FC:**

```
K₂ = 0
num(T) = 0.799×0.050 + 0.799×0.950 + 0.201×0.050 = 0.040 + 0.759 + 0.010 = 0.809
num(U) = 0.201 × 0.950 = 0.191
→ m*(T) = 0.809,  m*(U) = 0.191,  m*(F) = 0.0,  K = 0
```

**BetP(T) и Δ:**

> BetP(T) = 0.809 + 0.191 / 25 = 0.809 + 0.008 = 0.817
>
> s_c = 0.45  (45% учебных часов выделено на BACKEND)
>
> Δ = 0.817 − 0.45 = +0.367

**Решение:**

```
m*(F) = 0 < 0.8 → не obsolete
Δ = 0.367 > τ_Δ = 0.15  AND  K = 0 ≤ τ_K = 0.40
clearSignal = (m*(U) = 0.191 > τ_Θ = 0.15) → false
           → но Δ = 0.367 > 0.35 → clearSignal = true
Δ = 0.367 < 0.5 → recommendation = "moderate"
```

**Итог:** Для домена BACKEND рекомендация «умеренно увеличить» долю в РПД.
