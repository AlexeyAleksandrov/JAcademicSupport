Конечная цель DST — помочь методисту создать оптимальную РПД. Каждый уровень иерархии отвечает на один конкретный вопрос:

| № | Вопрос | Уровень | Пример ответа |
|---|--------|---------|---------------|
| **Q0** | **Покрытие доменов:** достаточно ли каждый домен представлен в РПД? Изменилась ли его важность для профессии? | 0 — Профессия → Домен | Δ(DevOps) = BetP(0.46) − supply(0.20) = +0.26 → дефицит; за 3 года вырос с 0.30 до 0.46 |

| **Q3** | **Актуальность версии:** та ли версия языка / библиотеки покрыта в РПД? | 3 — Навык → Версия | Java 8 в РПД vs медиана рынка Java 17 → effective_supply = supply × 0.10 → скрытый дефицит |

### Сравнение со старой трёхуровневой схемой

| Старая (3 уровня) | Новая (4 уровня) | Что изменилось |
|---|---|---|
| Профессия → Кластер | Профессия → **Домен** | Кластеры `skills_group` заменяются семантическими доменами `skill_canonical.domain` |
| — | **Домен → Tech Family** | Новый уровень тренд-анализа |

## Часть 3: Уровень 0 — Профессия → Домены (Q0)

### DST-формализация

**Фрейм:** Θ = {T — домен важен для профессии, F — не важен}

> **Ключевое разграничение:**  
> **STD** = ФГОС — государственный стандарт, внешний подтверждающий сигнал (требует ли государство данную компетенцию?)  
> **supply(РПД)** = покрытие в текущей рабочей программе дисциплины — то, что преподаватели *написали*. Это **не** источник DST, а **цель оптимизации**.  
> **Δ = BetP − supply(РПД)** = дефицит/избыток → рекомендация для методиста по изменению РПД.

**Источники для BPA:**

| Источник | λ | w | relevantCount | averageScore |
|---|---|---|---|---|
| VAC | 15 | 0.80 | вакансий профессии P с навыками домена D | avg score из `vacancy_cluster_score` |
| EXP | 5 | 0.90 | экспертов, оценивших D важным для P | avg оценка из `employer_skill_group` |
| FC | 2 | 0.60 | прогнозов роста для домена D | avg confidence |
| STD | 3 | 0.70 | компетенций ФГОС, относящихся к домену D | доля часов ФГОС на D / общий объём стандарта |

*STD-данные хранятся в `profession_cluster` (`source = 'fgos'`), заполняются ручным парсингом стандарта.*

Шаги 1–6 (κ → BPA → дисконтирование → Демпстер/Ягер → BetP → Δ) — из `ALGORITHM_CURRENT.md`.

**Обнаружение сдвига (Q0):**

Сдвиг выявляется при наличии истории `dst_results`:
```
shift(D, P) = BetP(D, P, t_current) − BetP(D, P, t_prev)
```
Если `shift > τ_shift` (например 0.10) → предупреждение: «Домен D стал значимо важнее для профессии P».

**Пример (Backend developer, текущее состояние БД):**

| Домен | weight (сейчас) | (цель) BetP | supply РПД | Δ | Решение |
|---|---|---|---|---|---|
| BACKEND | 0.95 | ≈ 0.85 | ? | ? | ? |
| DATABASE | 0.58 | ≈ 0.55 | ? | ? | ? |
| DEVOPS | 0.46 | ≈ 0.40 | ? | ? | ? |
| FRONTEND | 0.38 | ≈ 0.30 | ? | ? | ? |

*`weight` сейчас — частотный показатель. BetP и Δ — целевые показатели после подключения DST.*

## Часть 4: Уровень 1 — Домен → Технологические семейства (Q1)

### Q1: Достаточно ли покрыто семейство в РПД? Есть ли сдвиги?

**Инструмент:** DST (VAC + EXP + FC + STD) — те же 4 источника, что на L0, с уточнённой выборкой (добавляется фильтр `domain = D`).  
Тренд (Δ_trend = freq_current − freq_prev) вычисляется отдельно и входит как компонент `trend_factor` в FC-источник.

**DST-источники (область: вакансии профессии P в домене D):**

| Источник | λ | w | relevantCount | averageScore | Специфика L1 |
|---|---|---|---|---|---|
| VAC | 15 | 0.80 | вакансий P с навыками семейства F | relativeFrequency(F \| P, D) | фильтр: domain = D |
| EXP | 5 | 0.90 | экспертов, отметивших F перспективным | avg оценка | `employer_skill_group`, filter tech_family |
| FC | 2 | 0.60 | прогнозов роста спроса на F | avg confidence × trend_factor | данные из `forecast` + расчёт ниже |
| STD | 3 | 0.70 | компетенций ФГОС, касающихся семейства F | доля часов ФГОС на F / объём домена D | `profession_cluster` (`source='fgos'`), filter domain+family |

**Расчёт trend_factor (вход в FC):**
```
freq(F, t) = COUNT(вакансий P с навыками F) / COUNT(всех вакансий P)
Δ_trend(F) = freq(F, t_current) − freq(F, t_prev)
Δ_rel(F)   = Δ_trend(F) / freq(F, t_prev)

tend_factor = 1 + clamp(Δ_rel, −0.5, +0.5)   // > 1 если рост, < 1 если падение
```

**Пример (BACKEND, профессия backend):**

| Семейство | freq тек. | freq прош. | Δ_trend | BetP (цель) | supply РПД | Δ_supply | Решение |
|---|---|---|---|---|---|---|---|
| Java | 29% | 32% | −3% ↓ | ? | ? | ? | ? |
| Python | 27% | 22% | +5% ↑ | ? | ? | ? | ? |
| Go | 10% | 5% | +5% ↑↑ | ? | ? | ? | ? |
| PHP | 8% | 14% | −6% ↓↓ | ? | ? | ? | ? |

*Тренд требует снимков по периодам (`snapshot_date`). Сейчас доступен только Δ_supply (сравнение с РПД без истории).*

**Обнаружение сдвига (Q1):** при наличии истории в `dst_results`:
```
shift(F, D) = BetP(F, D, t_current) − BetP(F, D, t_prev)
```
Если `|shift| > τ_shift` → FC-сигнал усиливается, решение DST учтёт сдвиг автоматически.

## Часть 5: Уровень 2 — Семейство → Навыки стека (Q2)

### DST-формализация

**Фрейм:** Θ_u = {T — навык включить в РПД, F — не включать}

**Источники для BPA:**

| Источник | λ | w | relevantCount | averageScore | Специфика L2 |
|---|---|---|---|---|---|
| VAC | 15 | 0.80 | вакансий P с навыком U в семействе F | relativeFrequency(U \| P, F) | фильтр: tech_family = F |
| EXP | 5 | 0.90 | экспертов, считающих U важным в стеке F | avg оценка | `employer_skill_group`, filter по canonical |
| FC | 2 | 0.60 | прогнозов роста спроса на навык U | avg confidence | `forecast`; тренд навыка из `skill_domain_stats` |
| STD | 3 | 0.70 | компетенций ФГОС, упоминающих навык U явно | наличие/частота упоминания в требованиях | `profession_cluster` (`source='fgos'`); может быть null → m(Θ)=1 |

**CO-источник (дополнительный, только L2):** усиливает VAC-сигнал для косвенных зависимостей:
```
co_rate(U, ядро_F) = skill_dependency.co_count / COUNT(вакансий с U)
если co_rate > 0.8 → навык U «подразумевается» при работе с семейством F
m_co(T) = κ_co × co_rate   // вклад в BPA сверх 4 основных источников
```
В будущем `tech_implies` заменит `skill_dependency` с явными взвешенными рёбрами (Flask → Python).

**Пример выхода (семейство Java, профессия backend):**

| Навык | BetP | supply | Δ | Рекомендация |
|---|---|---|---|---|
| Spring Boot | 0.78 | 0.40 | +0.38 | 🔴 Усилить значительно |
| Java 17 | 0.65 | 0.20 | +0.45 | 🔴 Усилить значительно |
| Hibernate | 0.55 | 0.30 | +0.25 | 🟡 Усилить умеренно |
| Quarkus | 0.22 | 0.00 | +0.22 | 🟡 Рассмотреть включение |
| Struts | 0.08 | 0.20 | −0.12 | ⬇️ Сократить |

## Часть 6: Уровень 3 — Навык → Версии (Q3)

### version_currency коэффициент

```
Шаг 1: Определить рыночные ориентиры из version_group siblings:
  median_market = медианная версия по вакансиям
  max_market    = максимальная версия по вакансиям

Шаг 2: Вычислить отставание:
  version_gap = median_market − rpd_version   // со знаком

Шаг 3: Коэффициент актуальности:
  gap ≤ 0  → 1.00  (актуально или опережает)
  gap = 1  → 0.80  (небольшое отставание)
  gap = 2  → 0.50  (предупреждение)
  gap = 3  → 0.25  (значительное отставание)
  gap ≥ 4  → 0.10  (критическое устаревание)

Шаг 4: Скорректировать покрытие РПД:
  effective_supply = supply_skill × version_currency
```

**Интеграция с Уровнем 2:**  
На Уровне 2 в формуле дефицита используется `effective_supply`:
```
Δ(u) = BetP(u) − effective_supply(u)
```
Навык «Java» формально покрыт (supply = 0.3), но если учат Java 8 при median_market = Java 17:
- gap ≈ 9 мажорных версий → currency ≈ 0.10
- effective_supply = 0.3 × 0.10 = 0.03
- Δ = 0.65 − 0.03 = **0.62** → 🔴 Критический дефицит даже при формальном покрытии

**Что уже есть для Уровня 3:**

| Что нужно | Статус |
|---|---|
| `skill_canonical` siblings через `version_group` | ✅ Есть → отображение в UI |
| Частоты версий (`absoluteCount`) | ✅ Есть → из подсчёта вакансий |
| `median_version`, `max_version` | ⚠️ Вычислимо из siblings, нет отдельной таблицы |
| `skill_version_stats` (снимки по датам) | ❌ Нет |
| Версии навыков в РПД (`rpd_coverage.skill_version`) | ❌ Нет (`rpd_coverage` не создана) |

### Требуется создать

```sql
-- Граф зависимостей (Flask → Python). Заполняется из skill_dependency
-- где co_rate > 0.80, затем ручная валидация.
CREATE TABLE tech_implies (
    child_id   INT REFERENCES skill_canonical(id),
    parent_id  INT REFERENCES skill_canonical(id),
    weight     DECIMAL(3,2) DEFAULT 1.0,
    source     VARCHAR(20)  DEFAULT 'auto',   -- 'auto' | 'expert'
    UNIQUE(child_id, parent_id)
);

-- Покрытие РПД (ключевые данные для supply на всех уровнях)
CREATE TABLE rpd_coverage (
    id              SERIAL PRIMARY KEY,
    program_id      INT,
    domain          VARCHAR(50),
    tech_family     VARCHAR(100),
    canonical_id    INT REFERENCES skill_canonical(id),
    skill_version   VARCHAR(20),    -- '17', '3.11', '3.x'
    hours           INT,
    semester        INT,
    academic_year   INT,
    updated_at      TIMESTAMP DEFAULT NOW()
);

-- Статистика рыночных версий (для version_currency)
CREATE TABLE skill_version_stats (
    canonical_id     INT REFERENCES skill_canonical(id),
    snapshot_date    DATE,
    max_version      VARCHAR(20),
    median_version   VARCHAR(20),
    sample_size      INT,
    PRIMARY KEY (canonical_id, snapshot_date)
);

-- История результатов DST (для обнаружения сдвигов, Q0/Q1)
CREATE TABLE dst_results (
    id               SERIAL PRIMARY KEY,
    profession_code  VARCHAR(50),
    domain           VARCHAR(50),
    tech_family      VARCHAR(100),
    canonical_id     INT REFERENCES skill_canonical(id),
    level            INT,               -- 0, 1, 2, 3
    run_date         DATE,
    betp             DECIMAL(5,4),
    m_t              DECIMAL(5,4),
    m_u              DECIMAL(5,4),
    m_f              DECIMAL(5,4),
    k_conflict       DECIMAL(5,4),
    supply           DECIMAL(5,4),
    version_currency DECIMAL(3,2),
    effective_supply DECIMAL(5,4),
    delta            DECIMAL(5,4),
    recommendation   VARCHAR(20),
    params_json      JSONB
);

-- Добавить ФГОС-веса в profession_cluster
ALTER TABLE profession_cluster ADD COLUMN IF NOT EXISTS source VARCHAR(30) DEFAULT 'vacancy';
-- Строки с source = 'fgos' добавляются вручную или из парсинга стандартов
```
